# How IssuePilot works

This document is the guided map of the repository. It explains what belongs in
each file, why the file exists, and how the frontend, backend, and database work
together.

## Root files

| File | What belongs inside | Why it exists |
| --- | --- | --- |
| `AGENTS.md` | Repository-specific instructions, approval boundaries, required reading, and verification rules for coding agents | Agent behavior must be durable and visible instead of living only in chat history |
| `README.md` | Human introduction, technology, learning sequence, setup commands, and common checks | A new human contributor needs one obvious starting point |
| `.env.example` | Safe configuration names and non-secret example values | It teaches configuration without risking real credentials |
| `.gitignore` | Local databases, secrets, dependencies, caches, and generated output | These files should stay on a developer's machine and out of commits |

## Agent and environment files

| File | What belongs inside | Why it exists |
| --- | --- | --- |
| `.agents/skills/verify-change/SKILL.md` | A concise workflow for choosing and running IssuePilot checks before handoff | It makes verification repeatable for future coding-agent sessions |
| `.agents/skills/verify-change/agents/openai.yaml` | Display name, short description, and default prompt for the skill UI | It gives the skill clear human-facing metadata |
| `.codex/environment.toml` | Only environment configuration generated for this repository | The location is reserved without adding MCP servers, secrets, or machine-specific setup |

## Product and engineering documents

| File | What belongs inside | Why it exists |
| --- | --- | --- |
| `docs/SPEC.md` | User stories, data rules, acceptance criteria, and explicit non-goals | Product requirements should say what users need without prescribing code |
| `docs/ARCHITECTURE.md` | Component boundaries, data ownership, persistence choices, and approved technical decisions | Architecture should explain how the system is divided and why |
| `docs/API_CONTRACT.md` | Exact routes, request and response JSON, status codes, ordering, and errors | React and FastAPI need one shared source of truth |
| `docs/AI_BEHAVIOR.md` | Future classifier behavior, safety rules, and undecided AI boundaries | AI behavior needs separate review from ordinary application behavior |
| `docs/HOW_IT_WORKS.md` | This tree, file ownership, setup flow, runtime flow, and verification flow | A learner needs a guided explanation connecting all of the pieces |

## Frontend files

| File | What belongs inside | Why it exists |
| --- | --- | --- |
| `frontend/index.html` | The browser document, metadata, React root element, and module entry | Vite needs the HTML shell that loads the React application |
| `frontend/package.json` | Package identity, Node requirement, scripts, React dependencies, and Vite development dependencies | npm uses it to install and run the frontend |
| `frontend/package-lock.json` | The exact resolved npm dependency graph generated by `npm install` | Local installs and CI should receive the same versions |
| `frontend/vite.config.js` | React plugin setup and the local `/api` proxy to FastAPI | Frontend code can use relative API URLs without adding development CORS policy |
| `frontend/src/main.jsx` | React's connection to the `#root` element and the global stylesheet import | Entry-point wiring stays separate from screen behavior |
| `frontend/src/App.jsx` | Form state, issue list/detail state, loading and error states, and rendered MVP interface | The one-day MVP is small enough for one screen component |
| `frontend/src/api.js` | Fetch calls, JSON parsing, error normalization, and the three contract operations | HTTP details stay out of the visual component |
| `frontend/src/styles.css` | Global design tokens, layout, components, states, focus treatment, and responsive rules | Presentation remains separate from React behavior |

## Backend files

| File | What belongs inside | Why it exists |
| --- | --- | --- |
| `backend/requirements.txt` | Exact runtime versions for Anthropic, FastAPI, Pydantic, python-dotenv, and Uvicorn | A fresh environment can reproduce the API runtime and standalone Claude smoke test |
| `backend/requirements-dev.txt` | Runtime requirements plus Pytest, HTTPX2, Ruff, and Pyright | Development and verification tools do not need to be production dependencies |
| `backend/pyproject.toml` | Ruff formatting and lint rules plus Pyright type-checking settings | Local editors, agents, and CI should apply the same Python quality rules |
| `backend/pytest.ini` | Pytest discovery settings | The test command behaves consistently locally and in CI |
| `backend/app/__init__.py` | A short package marker and description | Python recognizes `app` as an explicit package |
| `backend/app/main.py` | FastAPI construction, startup database initialization, router registration, and safe unexpected-error handling | Application assembly stays visible in one entry point |
| `backend/app/database.py` | Database-path resolution, connections, and the SQLite schema | SQLite details have one owner and routes do not duplicate connection setup |
| `backend/app/models/__init__.py` | Package marker for API models | It names the responsibility of the package |
| `backend/app/models/issue.py` | Pydantic request/response models and title/description constraints | Validation and serialization implement the shared API contract |
| `backend/app/routes/__init__.py` | Package marker for route modules | It keeps HTTP modules in an explicit package |
| `backend/app/routes/issues.py` | Create, list, and get-one endpoints plus row-to-model conversion | All current issue HTTP behavior is easy to locate |
| `backend/tests/conftest.py` | A TestClient fixture configured with a fresh temporary database per test | Tests remain isolated and never touch the developer database |
| `backend/tests/test_issues.py` | Success, ordering, retrieval, not-found, and validation contract tests | The backend proves the documented behavior from a client's perspective |

## Future AI files

These locations exist now so their eventual responsibilities are easy to see.
Only `client.py` imports the Anthropic SDK, and it remains a standalone smoke test;
none of these modules participate in the running app.

| File | What will belong inside | Why it is empty or reserved now |
| --- | --- | --- |
| `backend/app/ai/__init__.py` | Package description and, only if useful later, stable public exports | It marks the future AI boundary |
| `backend/app/ai/client.py` | One small Responses API request using the ignored `.env` key and configurable model | It verifies SDK credentials and connectivity without changing product behavior |
| `backend/app/ai/schemas.py` | Approved Pydantic input and structured-output schemas | Exact enums and lifecycle still require approval |
| `backend/app/ai/service.py` | Prompt loading, model call orchestration, validation, and safe failure behavior | AI orchestration should stay out of HTTP routes |
| `backend/app/ai/tools.py` | Only explicitly approved model tools | No tool use is required for classification today |
| `backend/app/ai/prompts/triage_v1.md` | A versioned prompt whose output matches the approved schema | The file is a labeled placeholder, not an active prompt |
| `evals/triage_cases.json` | Representative inputs and expected behavioral properties | It is an empty JSON array until the AI schema is approved |

## What happens when the applications start

1. Uvicorn imports `app.main:app`.
2. FastAPI runs the lifespan function in `main.py`.
3. `database.py` loads the root `.env`, resolves `DATABASE_PATH` or uses
   `backend/issuepilot.db`, then creates the `issues` table if needed.
4. Vite loads `index.html`, which loads `src/main.jsx`.
5. `main.jsx` renders `App.jsx` and imports the stylesheet.
6. Vite proxies browser requests beginning with `/api` to FastAPI on port 8000.

## What happens when a user submits an issue

1. `App.jsx` trims the form values and catches obvious empty fields.
2. `api.js` sends `POST /api/issues` with JSON.
3. FastAPI matches the route in `routes/issues.py`.
4. Pydantic's `IssueCreate` model trims and validates the body again because
   browser validation can never be trusted as the security boundary.
5. The route inserts the validated values and a UTC timestamp into SQLite using
   parameterized SQL.
6. The stored row is validated as an `Issue` response model.
7. FastAPI serializes the model as the exact JSON in `API_CONTRACT.md`.
8. React places the returned issue at the top of the list, clears the form, and
   displays the saved issue details.

## What happens when issues are read

- On page load, `App.jsx` calls `GET /api/issues`. SQLite sorts by
  `created_at DESC, id DESC`, and the frontend renders the returned `items`.
- When a user selects a row, the frontend calls `GET /api/issues/{issue_id}` and
  displays the full returned issue.
- The frontend never creates IDs or timestamps and never accesses SQLite.

## How verification works

- Backend tests replace `DATABASE_PATH` with a new temporary database for each
  test, start FastAPI, and exercise the API through HTTP-style requests.
- Ruff checks Python formatting, import order, common style errors, and likely
  programming mistakes. Pyright checks type annotations and deprecated typing
  patterns without running the application.
- The frontend build asks Vite to parse, bundle, and optimize the React code,
  catching missing imports and syntax/build errors.
- The repository skill tells coding agents which checks to select and how to
  report them.
- GitHub Actions repeats the backend tests and frontend build on pushes and pull
  requests.

This is intentionally not production architecture. Authentication, editing,
deleting, pagination, deployment, and active AI triage remain outside the MVP.
