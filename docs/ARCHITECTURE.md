# IssuePilot architecture

## Status and change control

This is the planned architecture for the one-day MVP. It records technical
decisions, not product requirements or endpoint payloads. Changes to these
decisions require the repository owner's approval before implementation.

## System shape

IssuePilot is a single repository with two local applications:

```text
Browser
  -> React/Vite single-page interface
  -> JSON over HTTP under /api
  -> FastAPI application with Pydantic validation
  -> SQLite database file
```

All operations are synchronous request/response operations. There are no
background workers, queues, external services, or Claude calls in the MVP.

## Component responsibilities

### Frontend

The React frontend owns rendering, local form state, loading states, and
human-readable error display. It consumes the API exactly as documented in
`API_CONTRACT.md`. It does not generate IDs or creation timestamps and does not
connect to SQLite.

Vite supplies the development server and frontend build tooling. JavaScript is
used without TypeScript for this tutorial.

### Backend

The FastAPI backend owns HTTP routing, validation, issue creation and retrieval,
error responses, and timestamps. Pydantic models define request and response
boundaries. Database rows are converted into response models before leaving the
backend.

### Persistence

SQLite is the only persistence system. For the MVP, the backend uses Python's
standard `sqlite3` module, keeping the dependency surface and data path visible
to a learner. A single `issues` table contains:

| Column | SQLite representation | Rule |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY` | Generated by SQLite |
| `title` | `TEXT NOT NULL` | Validated before insert |
| `description` | `TEXT NOT NULL` | Validated before insert |
| `created_at` | `TEXT NOT NULL` | UTC ISO 8601 timestamp |

The database file defaults to `backend/issuepilot.db` and can later be
overridden with `DATABASE_PATH`. The database and table are initialized when the
backend starts. Schema migration tooling is outside the one-day MVP.

## Repository boundaries

In the current implementation:

- `frontend/` contains the Vite application;
- `backend/app/` contains the FastAPI application;
- `backend/tests/` contains Pytest tests; and
- `docs/` will continue to hold the decisions shared across the codebase.

Implementation details are split into small modules by responsibility. The MVP
does not need domain layers, dependency-injection frameworks, repositories, an
ORM, or a service mesh.

## Development boundary

During local development, the Vite server and FastAPI server run as separate
processes. The frontend uses a Vite development proxy for `/api` requests, so
application code uses relative API URLs and the backend does not need broad
CORS permissions for the normal local workflow.

Production serving and deployment topology are intentionally undecided.

## Error and data conventions

- JSON is the only API representation.
- Timestamps are generated by the backend in UTC and serialized as ISO 8601
  strings ending in `Z`.
- The backend trims surrounding whitespace before validating and storing title
  and description values.
- API errors use FastAPI's `detail` field as specified in `API_CONTRACT.md`.
- Persistence failures are not exposed to users as raw database messages.

## Future AI boundary

The future AI classifier will live behind the backend; the browser will never
hold an Anthropic API key or call Claude directly. The classifier will produce a
validated structured result and remain advisory. Its routes, persistence, and
execution model are intentionally not decided in this milestone.
